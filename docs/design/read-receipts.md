# طرح فنی: تیک «دیده شد» (Read Receipts)

| | |
|---|---|
| وضعیت | **مسدود (Blocked)**: فاز ۱ روی آخرین نسخهٔ Mattermost ممکن نیست (بخش ۲). پیاده‌سازی نشده |
| نسخهٔ هدف | 1.6.0 (فاز ۱)، 1.7.0 (فاز ۲، اختیاری) |
| ماژول جدید | `ReadReceipts` در `webapp/dist/main.js` |
| تاریخ | ۱۳ مهر ۱۴۰۵ |

## ۱. خلاصه

کنار ساعت پیام‌های **خودِ کاربر** یک یا دو تیک نمایش داده می‌شود:

| نشان | معنا | منبع داده |
|---|---|---|
| ✓ | پیام روی سرور ثبت شد | پیام `id` و `create_at` دارد (نه پیام pending) |
| ✓✓ (رنگی) | گیرنده بعد از ارسال، کانال را باز کرده | `last_viewed_at` گیرنده ≥ `create_at` پیام |

در کانال گروهی (GM) و کانال‌های کوچک به‌جای ✓✓ شمارنده نشان داده می‌شود: «✓✓ ۳/۵»، و با هاور اسامی بینندگان.

**تصمیم کلیدی:** فاز ۱ کاملاً **webapp-only** می‌ماند تا اصل معماری فعلی پروژه (نصب بدون باینری سرور) حفظ شود. هیچ دادهٔ جدیدی ذخیره نمی‌شود و فقط داده‌ای که Mattermost از قبل نگه می‌دارد نمایش داده می‌شود.

## ۲. منبع داده

Mattermost برای هر عضو هر کانال `ChannelMember.last_viewed_at` (میلی‌ثانیه) را نگه می‌دارد. هر بار که کاربر کانال را باز کند یا در آن باشد، این مقدار در وب، دسکتاپ و **موبایل** به‌روز می‌شود.

- خواندن: `GET /api/v4/channels/{channel_id}/members?page=0&per_page=…`
- فیلد مورد نیاز در پاسخ: `user_id` و `last_viewed_at`.

> ❌ **نتیجهٔ بررسی مفروض (۱۳ مهر ۱۴۰۵): رد شد.** در کد فعلی شاخهٔ `master` سرور Mattermost
> (`server/public/model/channel_member.go` و `server/channels/api4/channel.go`)، endpointهای اعضای کانال
> برای هر عضوی غیر از خودِ درخواست‌دهنده `SanitizeForCurrentUser` را صدا می‌زنند. این تابع `last_viewed_at`
> و `last_update_at` را با مقدار نگهبان `-1` جایگزین می‌کند و `MarshalJSON` آن‌ها را از پاسخ حذف می‌کند.
> یعنی Mattermost **عمداً** زمان بازدید دیگران را خصوصی می‌داند و از طریق REST به کاربر عادی نمی‌دهد.
> نسخه‌ای که این تغییر در آن منتشر شده بررسی نشده است. سرور هدف «آخرین نسخه» است، پس باید آن را شامل دانست.
>
> **پیامد:** فاز ۱ (webapp-only، گزینهٔ «الف») روی سرور هدف کار نمی‌کند. تنها مسیر فنی، بخش سرور پلاگین (فاز ۲) است
> که از Plugin API (`GetChannelMember`/`GetChannelMembers`) داده را بدون sanitize می‌خواند. این کار **نادیده گرفتن
> آگاهانهٔ یک تصمیم حریم خصوصی Mattermost** است و فقط با تصمیم صریح مدیر سیستم و اطلاع‌رسانی به کاربران قابل دفاع است.

## ۳. معماری فاز ۱ (webapp-only)

```
┌──────────── webapp (main.js) ────────────┐
│ ReadReceipts                              │
│  ├─ ChannelWatcher  ← تغییر کانال جاری    │
│  ├─ MemberCache     ← last_viewed_at      │
│  │    (TTL، dedupe، backoff)              │
│  ├─ Refresher       ← رویدادها + poll     │
│  └─ Renderer        ← data-attr + ::after │
└───────────────┬──────────────────────────┘
                │ REST v4 (کوکی نشست + X-CSRF-Token، همان helper فعلی Forward)
                ▼
        Mattermost server (بدون تغییر)
```

### ۳.۱ چه زمانی داده تازه می‌شود

| محرک | اقدام |
|---|---|
| ورود به کانال (DM/GM/کانال کوچک) | یک fetch |
| رویداد WebSocket `posted` در کانال جاری از طرف دیگران | fetch با debounce ۱ ثانیه (فرستادن پیام یعنی کانال را دیده) |
| ارسال پیام توسط خود کاربر | زمان‌بندی poll |
| poll دوره‌ای | فقط وقتی: تب visible است، کانال جاری پیام «✓ تنها» از خود کاربر در ۲۴ ساعت اخیر دارد. فاصله ۱۵s، با backoff تا ۶۰s در صورت عدم تغییر، و توقف کامل وقتی همه ✓✓ شدند |
| `visibilitychange` → visible | یک fetch |

ثبت رویداد WebSocket با `registry.registerWebSocketEventHandler('posted', …)` انجام می‌شود. توجه: رویداد `channel_viewed` فقط به خودِ بیننده ارسال می‌شود و برای اطلاع‌رسانی به فرستنده قابل استفاده نیست. به همین دلیل در فاز ۱ از poll استفاده شده است.

### ۳.۲ رندر

- طبق اصل پروژه (بدون دست‌کاری درخت React): روی ریشهٔ پیام `data-mmrtl-rr="sent|read"` و در صورت نیاز `data-mmrtl-rr-count="3/5"` گذاشته می‌شود و تیک با `::after` کنار زمان (همان جایی که `Stamps` تاریخ را می‌گذارد) رسم می‌شود.
- آیکون: SVG درون‌خطی طراحی‌شدهٔ خودمان (data URI در CSS). از آیکون یا رنگ برند پیام‌رسان‌های دیگر استفاده نمی‌شود.
- هاور/tooltip برای GM با `title` روی یک span سبک. اسامی از `entities.users.profiles` خوانده می‌شوند.
- ضد حلقه: همان الگوی `data-mmrtl-sig`. وضعیت فقط وقتی تغییر کند attribute بازنویسی می‌شود. MutationObserver موجود با `requestAnimationFrame` دسته‌بندی می‌شود.
- فقط پیام‌های کاربر جاری (`post.user_id === currentUserId`)، نه system message، و نه پیام‌های pending/failed (`pending_post_id` بدون `id` نهایی).

### ۳.۳ دامنهٔ کانال‌ها

تصمیم: قابلیت برای **همهٔ انواع کانال** فعال است. نحوهٔ نمایش و هزینهٔ دریافت داده بر اساس اندازهٔ کانال پله‌ای است:

| نوع / اندازه | نمایش | دریافت داده |
|---|---|---|
| DM (`D`) | ✓ / ✓✓ | یک درخواست |
| GM و کانال ≤ ۲۰ عضو | شمارنده + اسامی در tooltip | یک درخواست (`per_page=200`) |
| کانال ۲۱ تا ۲۰۰ عضو | شمارنده؛ tooltip حداکثر ۲۰ نام + «و N نفر دیگر» | یک درخواست |
| کانال > ۲۰۰ عضو | فقط شمارنده | صفحه‌بندی (۲۰۰تایی)، **بدون poll خودکار**؛ تازه‌سازی فقط هنگام ورود به کانال، `visibilitychange` و رویداد `posted`، با حداقل فاصلهٔ ۶۰ ثانیه |
| DM با خود، DM با بات | غیرفعال | — |

- شمارنده فقط اعضای انسانی و فعال را حساب می‌کند. بات‌ها، کاربران غیرفعال و خود فرستنده کنار گذاشته می‌شوند.
- مخرج کسر برابر تعداد اعضای کانال **در لحظهٔ نمایش** است، نه لحظهٔ ارسال (Mattermost تاریخچهٔ عضویت را در این API نمی‌دهد). عضوی که بعداً اضافه شود و کانال را ببیند، جزو بینندگان پیام‌های قدیمی هم حساب می‌شود. این محدودیت در بخش ۵ ثبت شده است.
- اگر تعداد عضو نامعلوم باشد، فقط ✓ نمایش داده می‌شود (fail-closed).
## ۴. حریم خصوصی و کنترل‌ها

**حقیقت مهم:** در فاز ۱، `last_viewed_at` از قبل از طریق API برای اعضای کانال قابل خواندن است. پلاگین داده‌ای را افشا نمی‌کند که API افشا نکرده باشد، ولی آن را **قابل‌مشاهده** می‌کند. هر کنترل سمت کلاینت (مثل opt-out) **نمایشی** است و جلوی کاربری را که مستقیم API را صدا بزند نمی‌گیرد. این موضوع باید شفاف به سازمان گفته شود.

کنترل‌ها:

1. **تنظیم کاربر** (در بخش تنظیمات فعلی پلاگین): «نمایش تیک دیده‌شدن» — **پیش‌فرض خاموش**.
2. **سوئیچ مدیر:** در webapp-only، تنظیمات `settings_schema` در System Console برای کاربر عادی قابل خواندن نیست. در فاز ۱ کنترل مدیر = فعال/غیرفعال کردن یا عدم ارتقای خود پلاگین. سوئیچ واقعی مدیر و **قاعدهٔ دوطرفه** (کسی که opt-out کند تیک دیگران را هم نبیند) فقط با فاز ۲ قابل اعمال سمت سرور است.
3. قبل از فعال‌سازی در سازمان، اطلاع‌رسانی به کاربران.
4. هیچ داده‌ای ذخیره، لاگ یا به سرویس بیرونی ارسال نمی‌شود.

## ۵. محدودیت‌های شناخته‌شده

- ✓✓ یعنی «کانال باز شد»، نه «پیام دیده شد». اگر کاربر بالای صفحه باشد یا تب در پس‌زمینه باز مانده باشد، باز هم ✓✓ می‌خورد. اگر کاربر پیام را فقط در **نوتیفیکیشن** یا پیش‌نمایش ببیند، ✓✓ نمی‌خورد.
- پاسخ‌های thread (CRT): `last_viewed_at` کانال لزوماً دیده‌شدن thread را نشان نمی‌دهد. در فاز ۱ تیک فقط برای پیام‌های ریشه نمایش داده می‌شود.
- «تحویل به دستگاه» (delivered) معادلی ندارد. ✓ فقط یعنی ثبت روی سرور.
- اپ **موبایل** تیک‌ها را نمایش نمی‌دهد (پلاگین وب اجرا نمی‌شود)، ولی دیدن پیام در موبایل باعث ✓✓ در وب/دسکتاپ فرستنده می‌شود.
- تأخیر نمایش ✓✓ تا ۱۵–۶۰ ثانیه (poll)؛ در کانال‌های > ۲۰۰ عضو تا بازدید/رویداد بعدی.
- در کانال‌های گروهی، مخرج شمارنده اعضای فعلی است، نه اعضای لحظهٔ ارسال.
- وابستگی به ساختار DOM پست و زمان؛ مثل `Stamps` ممکن است با ارتقای Mattermost نیاز به به‌روزرسانی selector داشته باشد.

## ۶. عملکرد و مقیاس

- حداکثر یک درخواست هم‌زمان برای هر کانال (dedupe)، و فقط برای **کانال جاری**.
- Poll فقط در تب visible و فقط تا وقتی پیام «✓ تنها» وجود دارد. در حالت پایدار درخواستی ارسال نمی‌شود.
- برآورد بدترین حالت: N کاربر فعال که هم‌زمان در DM منتظرند ≈ N/15 درخواست در ثانیه، که با backoff کاهش می‌یابد. برای چند صد کاربر ناچیز است. برای چند هزار کاربر فاز ۲ توصیه می‌شود.
- خطای HTTP (403/429/5xx): تیک‌ها در وضعیت ✓ می‌مانند (هرگز ✓✓ اشتباه نشان داده نمی‌شود)، backoff نمایی تا ۵ دقیقه، و فقط `console.debug`.

## ۷. فاز ۲ (اختیاری): بخش سرور Go

فقط اگر یکی از این‌ها لازم شد: سوئیچ واقعی مدیر، قاعدهٔ دوطرفه، به‌روزرسانی آنی، مقیاس بالا، یا اگر مفروض بخش ۲ رد شد.

- endpoint `GET /plugins/{id}/api/v1/read-status?channel_id=` با چک عضویت درخواست‌دهنده (`HasPermissionToChannel`)، اعمال تنظیمات مدیر و opt-out کاربران **سمت سرور**.
- اطلاع آنی: کلاینت گیرنده پس از `channel_viewed` به پلاگین خبر می‌دهد و پلاگین با `PublishWebSocketEvent` فقط برای اعضای همان کانال broadcast می‌کند. poll کم‌تکرار به‌عنوان fallback برای بازدیدهای موبایل باقی می‌ماند.
- **هزینه:** پروژه از «فقط آپلود یک JS» به باینری چندپلتفرمی Go، CI build و سازگاری با Plugin API تبدیل می‌شود. این تغییر یک تصمیم معماری جداگانه است.

## ۸. برنامهٔ آزمون

بدون فریم‌ورک تست در مخزن (وضعیت فعلی)، حداقل‌ها:

1. `node --check` (از طریق `scripts/package.sh`).
2. استخراج منطق خالص در توابع قابل‌آزمون — `receiptState(post, members, currentUserId)` و `shouldPoll(...)` — و آزمون واحد با `node --test` (بدون وابستگی جدید) برای:
   - DM خوانده‌نشده/خوانده‌شده، مرز `last_viewed_at === create_at`
   - GM با شمارش جزئی، خروج عضو از کانال
   - پیام pending/failed/system، پیام دیگران
   - کانال بزرگ‌تر از سقف و تعداد عضو نامعلوم ← غیرفعال
3. آزمون دستی روی Mattermost ۹.۰ و 11.11: وب و دسکتاپ، تم روشن/تیره، RTL/LTR، بازدید گیرنده از موبایل، قطع شبکه و 403.
4. پیش از کدنویسی: **آزمون مفروض بخش ۲** با یک کاربر غیرادمین.

## ۹. انتشار و بازگشت
