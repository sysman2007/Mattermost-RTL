# Design: پوشه‌های پیام (شخصی، مخاطب، اشتراکی و گروهی)

وضعیت: **تأیید شده — آماده برای پیاده‌سازی** (تصمیم‌های بخش ۱۱). هنوز کدی نوشته نشده است.

## ۱. هدف

کاربر بتواند پیام‌های مرتبط (مثلاً اسکریپت‌های دیتابیس) را در پوشه‌هایی نگه دارد که:

| نوع | چه کسی می‌بیند | چه کسی ایجاد می‌کند | ایجاد | حذف |
|---|---|---|---|---|
| **شخصی** | فقط مالک | مالک | بدون تأیید | بدون تأیید |
| **مخاطب** (per-contact) | فقط مالک؛ مرتبط با یک مخاطب | مالک | بدون تأیید | بدون تأیید |
| **اشتراکی** (دونفره) | مالک + یک عضو | مالک | **با تأیید عضو** | **با تأیید عضو** |
| **گروهی** | مالک + اعضای گروه | مالک | **با تأیید همهٔ اعضا** | **با تأیید همهٔ اعضا** |

> برداشت: «پوشهٔ مخاطب» یعنی پوشه‌ای که فقط مالک می‌بیند و به یک مخاطب مشخص مربوط است؛ مخاطب در آن هیچ دسترسی ندارد. این مدل تأیید شده است.

## ۲. غیرهدف‌ها (نسخهٔ اول)

- همگام‌سازی با اپ موبایل (فقط وب).
- پوشه‌های تودرتو.
- اشتراک‌گذاری لینک عمومی.
- نسخهٔ پیام در پوشه (ذخیره فقط شناسهٔ پیام است).
- ویرایش پیام از داخل پوشه.

## ۳. مدل داده (KV پلاگین)

KV پلاگین کلید/مقدار است و جدول یا کوئری ندارد. طراحی بر این اساس است:

| کلید | مقدار | نکته |
|---|---|---|
| `f:<fid>` | `{id, name, kind, owner, members[], created_at, status}` | متادیتای پوشه |
| `fi:<fid>:<post_id>` | `{channel_id, added_by, added_at}` | هر آیتم کلید جدا دارد (بدون قفل فهرست) |
| `fu:<uid>` | فهرست `fid`های کاربر | ایندکس، با CAS به‌روز می‌شود |
| `fr:<rid>` | درخواست تأیید (ایجاد/حذف/دعوت) | `status`: pending، approved، rejected، expired |

- **همزمانی:** هر به‌روزرسانی فهرست `fu:<uid>` و متادیتای `f:<fid>` با `KVSetWithOptions(..., Atomic: true, OldValue: ...)` انجام می‌شود. اگر مقدار تغییر کرده باشد، یک بار دوباره خوانده و تلاش می‌شود (حداکثر سه بار).
- **حذف:** ابتدا `status = deleting` و بعد با تأیید همه، آیتم‌ها و متادیتا پاک می‌شوند. اگر فرایند نیمه‌تمام ماند، یک کار تعمیر (در هر خواندن) وضعیت را جمع می‌کند.
- **انقضا:** درخواست‌های تأیید‌نشده پس از **۷ روز** `expired` می‌شوند (`ExpireInSeconds` یا بررسی زمان در خواندن).

## ۴. قواعد دسترسی (سرور، هر درخواست)

۱. کاربر باید در `members` باشد (برای شخصی و مخاطب: همان مالک).
۲. هنگام **خواندن** یک آیتم: کاربر باید `HasPermissionToChannel(ReadChannelContent)` برای کانال آن پیام داشته باشد؛ در غیر این صورت آیتم **پنهان** می‌شود (حذف نمی‌شود).
۳. هنگام **افزودن** پیام: کاربر باید خودش به پیام دسترسی داشته باشد (`GetPost` + دسترسی کانال). شناسهٔ پیام حدسی پذیرفته نمی‌شود.
۴. پیام **حذف‌شده** (`DeleteAt != 0`) در خواندن نادیده گرفته و در یک کار دوره‌ای پاک می‌شود.
۵. هیچ‌گاه متن پیام ذخیره نمی‌شود؛ پاسخ API فقط متادیتا و متن زنده‌ای است که کاربر حق خواندنش را دارد.

## ۵. گردش تأیید

**ایجاد پوشهٔ اشتراکی/گروهی:**
1. مالک پوشه و لیست اعضا را می‌فرستد. سقف کل اعضا (شامل مالک) **۸ نفر** است، همان `ChannelGroupMaxUsers` در `model/channel.go` از `server/public v0.5.0`.
2. وضعیت پوشه `pending` است و هر دعوت‌شده درخواست تأیید می‌گیرد.
3. وقتی همهٔ اعضا تأیید کردند → `active`. اگر یکی رد کند یا منقضی شود → پوشه حذف می‌شود.
4. اعلان: نشانگر در UI (تعداد درخواست‌های در انتظار). بدون پیام خصوصی از ربات.

**حذف پوشهٔ اشتراکی/گروهی:**
1. هر عضو می‌تواند درخواست حذف بدهد → `fr:` با `kind=delete`.
2. با تأیید **همهٔ** اعضا، پوشه حذف می‌شود. رد یک عضو درخواست را می‌بندد.
3. پوشهٔ مالک‌دار شخصی/مخاطب بدون تأیید حذف می‌شود.

**ترک پوشهٔ اشتراکی/گروهی:** آزاد است (بدون تأیید). پس از ترک، اگر پوشه یک عضو باقی نماند، پوشه با همان عضو باقی‌مانده ادامه می‌یابد و مالک آن (در صورت ترک مالک) به اولین عضو باقی‌مانده **منتقل** می‌شود.

## ۶. API سرور (پیشنهادی)

| مسیر | کار |
|---|---|
| `GET /api/v1/folders` | فهرست پوشه‌های کاربر |
| `POST /api/v1/folders` | ایجاد (شخصی/مخاطب فوری؛ اشتراکی/گروهی → pending) |
| `GET /api/v1/folders/{id}` | متادیتا و آیتم‌های قابل‌دیدن |
| `POST /api/v1/folders/{id}/items` | افزودن پیام |
| `DELETE /api/v1/folders/{id}/items/{post_id}` | حذف آیتم |
| `POST /api/v1/folders/{id}/delete-requests` | درخواست حذف |
| `GET /api/v1/requests` | درخواست‌های تأیید در انتظار کاربر |
| `POST /api/v1/requests/{rid}/approve` · `/reject` | پاسخ به درخواست |

همهٔ مسیرها `Mattermost-User-Id` را می‌خوانند؛ بدون آن ۴۰۱.

## ۷. UI (وب)

- منوی هاور پیام: «افزودن به پوشه…» (فقط اگر ویژگی روشن است).
- پنل کناری «پوشه‌ها» با تب‌های شخصی / مخاطب / اشتراکی / گروهی.
- نشانگر تعداد درخواست‌های تأیید.
- همهٔ متن‌ها دوزبانه (فارسی/انگلیسی) مطابق بقیهٔ افزونه.

## ۸. امنیت و ریسک‌ها

- **نشت پیام:** کنترل دسترسی در سرور است، نه در مرورگر. هر خواندن دوباره بررسی می‌شود.
- **حدس شناسه:** شناسهٔ پیام‌های دیگران پذیرفته نمی‌شود (قاعدهٔ ۳).
- **اسپم درخواست:** سقف درخواست‌های pending برای هر کاربر (پیشنهاد: ۲۰).
- **سقف‌ها:** ۲۰۰ پوشه برای هر کاربر؛ ۵۰۰ آیتم برای هر پوشه (قابل تنظیم در System Console).
- **فعال/غیرفعال:** ویژگی پشت تنظیم سیستم است؛ خاموش بودن باعث 404 می‌شود و داده‌ها پاک نمی‌شوند.
- **کاربر غیرفعال‌شده:** از اعضا حذف می‌شود و پوشه‌های مالکانه‌اش به اولین عضو باقی‌مانده منتقل می‌شود (بخش ۱۱).

## ۹. آزمون‌ها

- **Go (plugintest):** دسترسی هر مسیر؛ CAS و تلاش مجدد؛ رد/انقضای درخواست؛ حذف نیمه‌تمام و تعمیر؛ پنهان شدن آیتم برای کاربری که دسترسی کانال ندارد؛ شناسهٔ پیام دیگران پذیرفته نمی‌شود.
- **Node:** منطق UI (مدل داده در مرورگر) و ترجمه‌ها.
- **E2E (Mattermost واقعی):** سه کاربر؛ ایجاد گروهی با تأیید؛ حذف با تأیید؛ حذف دسترسی یک کاربر به کانال و بررسی پنهان شدن آیتم.

## ۱۰. استقرار و بازگشت

- ویژگی پشت تنظیم است و به‌صورت پیش‌فرض **خاموش** منتشر می‌شود.
- اگر مشکل بود: خاموش کردن تنظیم بدون حذف داده، و در صورت لزوم پاک‌سازی KV با اسکریپت.
- نسخه پیشنهادی: 2.4.0 (ویژگی جدید).

## ۱۱. تصمیم‌ها (تأیید شده)

1. **ترک پوشهٔ اشتراکی/گروهی:** آزاد. مالکیت در صورت ترک مالک به اولین عضو باقی‌مانده منتقل می‌شود.
2. **کاربر غیرفعال‌شده:** پوشه‌های مالکانه‌اش به اولین عضو باقی‌مانده منتقل می‌شود. اگر عضو باقی‌مانده‌ای نباشد، پوشه حذف می‌شود.
3. **سقف اعضای گروه:** ۸ نفر (شامل مالک)، مطابق `ChannelGroupMaxUsers` در کد عمومی Mattermost.
4. **اعلان تأیید:** نشانگر در UI (تعداد درخواست‌های در انتظار)، بدون پیام خصوصی از ربات.

## ۱۲. انطباق با قوانین

- طراحی فقط بر پایهٔ API عمومی پلاگین Mattermost (`public v0.5.0`) و مستندات آن است. کدی از Mattermost کپی نمی‌شود.
- از کد یا دارایی‌های دارای مجوز دیگر استفاده نمی‌شود؛ هر وابستگی جدیدی باید مجوزش بررسی و ثبت شود.
